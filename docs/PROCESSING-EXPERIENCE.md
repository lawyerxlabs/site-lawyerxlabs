# Processing experience — technical specification

**Status:** Design agreed; implementation coverage requires verification. **Date:** 2026-10-31.
**Decision:** [ADR 0008](adr/0008-processing-experience.md). Shared processing UI and several integrations exist in the repository; this specification does not establish full acceptance or deployment.

## Scope and contract

Apply the pattern to the MVP `JobStatus`, compatible `JobWorkflowPanel`, Term Isolation, Transaction Review, HR Hiring and HR Onboarding. The dedicated view replaces the intake content when the user submits a valid source and remains until a result, decision, or actionable failure is available. It is inside the existing workflow frame, not a new browser route. Start feedback at request initiation, including upload, so a slow response is visible. If submission fails, restore the relevant intake and show the error without losing input unless the existing lifecycle requires it.

For a request initiated after an intermediate decision, put the same indicator and message inline near the initiating action, retaining the decision and its relevant context. Disable duplicate submission while the operation is in flight. Preserve any existing supported replace/cancel action and its race guards; do not add cancellation by assuming a request can be cancelled. On settlement, show the returned next state or error. A shared presentational component may accept a label and display mode, but state, requests, cleanup and recovery stay in the owning panel. Reuse the existing indeterminate `Progress` where appropriate; no new backend API or common state machine is required.

### Mapping from current frontend evidence to required presentation

| Owner and operation | Observable state today | Required presentation |
| --- | --- | --- |
| MVP `App` / `JobStatus` | Upload `busy`; job `queued`, `processing`, `completed`, `failed`, `rejected`, `purged`; result loading; poll error. | Dedicated view during upload and active job. Map queued to waiting and processing to preparing; completed may show loading only while result requests are pending. Show result or appropriate terminal error afterward. Poll failure is a status-check error, not proof of job failure; preserve the existing manual status retry and supported cancel behavior. |
| `JobWorkflowPanel` / `useWorkflowJob` | Upload `busy`; base job status and optional workflow `queued`, `running`, `completed`, `failed`; artifact load after valid completed workflow. `needsPolling` includes an unfinished workflow after base completion. | Dedicated view through upload, base processing, reported workflow work and artifact loading. Use reported states only. Do not show ready merely because the base job completed; validate workflow identity/status and artifact as today. Preserve reset and source cleanup. |
| `TermIsolation` | One busy interval covering submit then one-time artifact take; no exposed substage. | One dedicated “Extracting terms from the agreement…” pending message until the combined operation settles; never retry the one-read take automatically. Keep the source in component state for the result preview and preserve its one-time result notice. |
| `TransactionReview` | One busy session-create request; review follows. | Dedicated “Preparing transaction review…” while pending; show the returned review or mapped error. Keep template mismatch recovery and existing source/session cleanup. Review field edits are local and do not themselves initiate processing. |
| `HrHiring` | Session creation prepares the source; generation follows criteria decisions; one `busy` flag covers both. | Dedicated “Preparing job description…” during creation. Inline “Generating improved job description…” after decisions, retaining preview and criteria. Distinguish operations in presentation without changing request invalidation or session deletion. |
| `HrOnboarding` | Session creation, classification confirmation, and generation have pending requests; generation has a separate `generating` flag. | Dedicated “Preparing documents…” during creation. Inline “Confirming document types…” during confirmation and “Generating checklist…” during generation; retain classifications. Preserve the existing per-error action mapping and single in-flight generation guard. |

Labels above are proposed copy, not backend stage names. A single pending operation should not cycle through multiple messages. For jobs, map actual state changes only; handle unknown or missing workflow state conservatively rather than claiming completion. `JobStatus` and `JobWorkflowPanel` have different result contracts and must retain their existing terminal and polling rules. Other registered panels, including Docalias and Agreement Review, require an operation-by-operation audit before adopting this pattern; do not infer their semantics from this table.

## Interaction and visual behavior

- Show an identifiable heading, concise workflow-specific pending text and an indeterminate progress indicator. No numeric value, time estimate, invented stage, or implied completion. Keep the frame and navigation consistent with the existing page; do not expose filenames or source contents unnecessarily.
- Announce meaningful state changes through a stable polite status region (`role="status"`); avoid duplicate live announcements from both the text and the indicator. Give the progressbar a meaningful accessible name, with no `aria-valuenow` when indeterminate. Announce actionable failures once, with a clear heading and supported action. Do not steal focus on every update; when replacing the intake or showing a result/error, manage focus to a sensible heading or action and test keyboard and screen reader behavior.
- At narrow widths stack content and actions, allow long text to wrap, and avoid horizontal clipping or loss of controls. At larger widths keep the processing message readable within the workflow frame. Respect reduced-motion preferences; the existing progress CSS disables its animation in that mode. Status must remain understandable without color or animation.
- Do not display advice to keep the page open, leave safely, or expect recovery after refresh until the particular operation's lifecycle is verified. Likewise do not add claims about deletion, AI transmission, privacy, persistence or source storage without evidence for that operation. Existing verified notices and warnings remain in their appropriate state.

## Failure and lifecycle rules

Use the existing error translation and operation-specific recovery; do not show raw server messages where a panel intentionally maps them. Distinguish submission failure, status polling failure, terminal failure/rejection/purge, expired or unavailable results, and result retrieval failure. A status retry must only recheck status; it must not resubmit a source or reread a consumed artifact. Offer retry, replace, start over, sign-in, or cancel only where the relevant contract and current state support it. Never offer an automatic retry of a read-once result. In ambiguous network outcomes, do not claim processing did not occur or promise a result can be retrieved again.

Preserve the existing job polling stop/error behavior, source stores, expiration and purge handling, single-flight guards, stale-response suppression and session cleanup. In particular, `TermIsolation` takes its artifact once, `JobWorkflowPanel` caches the read-once artifact request across remounts, MVP result artifacts have their own read-once handling, and onboarding generation is guarded and not automatically retried. Presentation must not trigger extra requests on rerender or remount. Retain existing auth, handling selection, Turnstile, source validation and endpoint boundaries. Do not change partial-result behavior or infer it across workflows.

## Acceptance and verification

1. With a delayed source request, each in-scope panel shows the dedicated view immediately; after a successful response it advances only to the actual next state. Initial failures return to the appropriate actionable state. An intermediate HR confirmation or generation keeps relevant review context and uses inline feedback.
2. Exercise queued → processing → completed and workflow queued/running → completed, plus missing/mismatched workflow, terminal failures, purge/expiry, result loading and poll failure. Assert messages follow supplied states, no fabricated percentage or timer changes occur, and a poll retry does not resubmit or fetch an artifact again.
3. For each one-shot/session flow, delay and reject requests; test duplicate clicks, replace/unmount during an in-flight request, late responses, cleanup, source preservation and the existing error-specific actions. Assert no automatic repeat of read-once retrieval or generation. Retain existing artifact and cancellation regression tests.
4. Test status and error announcements, progress accessible name and indeterminate semantics, keyboard focus and controls, reduced motion, and narrow/wide layouts. Include manual screen-reader and responsive checks; automated DOM assertions alone do not establish usability.
5. Run `npm test` and `npm run build`, plus focused component tests for the changed panels. Perform authenticated synthetic-source smoke tests against the relevant enabled services and verify page-close/refresh behavior separately before publishing lifecycle guidance. No real client documents are needed.

## Evidence and limitations

Based on `src/App.tsx`, the six panels named above, `src/lib/api.ts`, `src/lib/useWorkflowJob.ts`, `src/lib/pollJob.ts`, `src/components/ui/progress.tsx`, and existing job-status tests. This is a frontend source review, not a running end-to-end or backend lifecycle verification. Page-close behavior, actual service transitions, supported recovery under ambiguous network failures, and screen-reader behavior remain to be verified during implementation. Any discrepancy between deployed service behavior and the frontend mapping must be resolved before adding corresponding copy or changing recovery.
